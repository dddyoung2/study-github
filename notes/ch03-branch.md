# ch03. branch
> 깃에서 쓰이는 브랜치에 대해서 공부했습니다.

## 브랜치 관련 개념
- 브랜치 활용 방식
    - 협업하는 기반이 됨
    - 각 담당자가 새로운 브랜치를 생성, 분리되어 별도 공간에서 개발함. 즉, 공통된 정보를 소유하고 있는 main에서 시작하여 각자가 담당한 새로운 기능들을 별도 공간에서 개발!
    - 완성이후, 브랜치를 병합하여 전체를 통합
- 브랜치 유의 사항
    - 한 브랜치를 오래 갖고 있으면 main과의 차이가 심해 merge 하는 도중 충돌 확률이 매우 높아짐
    - 기능별 잘 나누어 한 브랜치를 갖고 있는 시간을 최소화하고, 완료하면 바로 main 병합 준비를 해야함
    - 별도 공간을 바라보고 있지만 협업의 과정에서 겹치는 부분을 건드리게 되면 병합에 있어 충돌이 발생하므로 브랜치를 작게작게 갖고 있어야 함
- main 브랜치: git이 기본적으로 생성하는 브랜치. 즉, 시작점이므로 보통 병합을 하면 이 브랜치에 합침. 예전에는 master 브랜치라고 불렀다고 함.
- HEAD Pointer: 현재 작업 중인 로컬 브랜치를 가리킴.
    - `main`에서 작업 중이면 HEAD -> `main`
    - `feat/user-admin` 브랜치에서 작업 중이면 HEAD -> `feat/user-admin`

## 명령어
- `git branch`: 존재하는 branch 확인 명령어
- `git branch {branch-name}`: branch를 생성하는 명령어
    - opt
        - `--merged`
        - `--no-merged`
        - `-d`
        - `-D`: **브랜치 삭제 강제 옵션**
- `git checkout {branch-name}`: HEAD를 지정한 브랜치로 이동시키는 명령어.
    - opt
        - `-b`: `git branch {branch-name}` + `git checkout {branch-name}`을 할 수 있음
- `git remote`
    - opt
        - `add`
        - `-v`
        - `show`
- `git fetch`

## 상황 시나리오
> 작업 중인 웹사이트가 있는데, 새로운 이슈가 발생하여 이를 처리하려 한다. 그러고자 새 브랜치를 생성하고 이동하여 이슈 작업을 진행한다.  
> 또, 버그나 보안 취약점의 중요한 문제가 발생해 Hotfix를 먼저 만들어야 한다. 새로운 이슈를 처리하기 이전에 처리해야 하며, 이슈처럼 새 브랜치를 만들어 작업 후, 테스트를 마치고 머지한 다음 작업을 이어간다.

### 이슈 처리
1. 이슈 처리용 브랜치 생성 및 이동
2. 이슈 처리 후 커밋
3. 메인 브랜치로 복귀
4. Hotfix 처리 완료 후 이슈 추가 작업 진행 및 구현 완료
5. 메인 브랜치와 이슈 브랜치 병합
6. 불필요한 이슈 브랜치 삭제

### 버그나 보안 취약점 처리
1. Hotfix용 브랜치 생성 및 이동
2. Hotfix 처리 후 커밋
3. 문제 해결 여부를 판단하기 위해 테스트 수행
4. 이슈 브랜치보다 먼저 메인 브랜치와 Hotfix 브랜치 병합
5. 다 써서 쓸 일 없는 Hotfix 브랜치 삭제

### 충돌 발생
- 3-way merge가 실패하는 경우 충돌이라고 함
- 병합할때 두 브랜치에서 같은 파일의 한 부분을 동시에 수정하고 머지할 때 발생. 충돌 발생 시 문제점 확인 및 수정 후 작업 재개해야 함
- 충돌을 수정하려면 편집기로 문서를 수정하고 저장하여야 함
